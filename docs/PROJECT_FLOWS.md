# 项目 Q&A 面试讲解稿

本文档按“大厂面试官追问”的方式整理 FZU Homework Assistant。回答尽量围绕项目难点、亮点、解决方案和可量化结果，适合用于简历深挖、项目复盘和面试讲解。

## 一、项目整体

### Q1：你先用一两分钟介绍一下这个项目，它解决了什么问题？

A：这个项目是一个面向课程作业场景的 AI 报告生成与质量监控系统。用户创建作业、上传 PDF、Markdown 或 TXT 课程资料后，系统会自动解析资料、构建作业级向量索引，然后根据作业内容识别任务类型，基于 RAG 生成中文 Markdown 报告，并通过质量门控判断报告是否需要自动改写。

它不是简单调用大模型生成一段文本，而是做了一条完整的 Agent 闭环：资料解析、向量检索、任务路由、报告生成、质量审稿、自动改写、再次优化、任务日志和监控统计。我的核心目标是让生成内容更贴合课程资料、更符合不同作业类型的结构，并且让 Agent 的运行过程可追踪、可评估、可优化。

一句话概括就是：我做的是一个带作业级 RAG、任务类型识别、质量门控、自动改写和可观测监控的作业报告生成 Agent 系统。

### Q2：这个项目的技术栈和模块划分是怎样的？

A：项目是一个多模块架构：

- 前端使用 Next.js 14、React、TypeScript、Tailwind CSS，主要负责作业管理、资料上传、报告预览编辑、任务进度展示和监控面板。
- 后端使用 Spring Boot 3、Java 21、MyBatis Plus、MySQL，负责业务数据、文件存储、异步任务编排、SSE 日志推送和报告版本管理。
- Agent 服务使用 FastAPI，接入 OpenAI-compatible SDK、DeepSeek、DashScope text-embedding、ChromaDB 和 pypdf，负责资料解析、向量化、RAG 检索、Skill 路由、报告生成、质量检查和改写。
- 工程化方面用 Docker Compose 管理前后端、Agent、MySQL 和 ChromaDB，同时有单元测试、离线评测脚本和监控数据沉淀。

整体数据流是：

```text
Next.js 前端 -> Spring Boot 后端 -> FastAPI Agent -> ChromaDB / LLM / Embedding
```

### Q3：为什么要拆成 Java 后端和 Python Agent 两个服务？直接一个后端做完不行吗？

A：主要是基于职责边界和生态考虑。Java 后端更适合承载稳定的业务系统能力，比如作业、资料、任务、报告、日志这些结构化数据的管理，也适合处理异步任务、SSE 推送和 MySQL 持久化。

Python Agent 则更适合 AI 链路开发，生态上更方便接入 embedding、ChromaDB、PDF 解析、Prompt 编排和后续评测脚本。如果把所有能力都塞到一个服务里，业务逻辑和 Agent 实验逻辑会耦合在一起，后续调 RAG、Prompt、质量门控都会影响主业务服务。

所以我把 Java 后端作为任务编排和业务中台，把 Python Agent 作为可独立迭代的智能能力服务。这样业务链路稳定，Agent 链路也更容易快速实验和替换模型。

## 二、核心业务流程

### Q4：从用户点击“生成报告”开始，系统内部完整流程是什么？

A：完整流程可以分成九步：

1. 用户在前端创建作业并上传资料。
2. 后端保存资料文件，并在 `materials` 表记录文件状态。
3. 用户点击生成报告后，后端创建一条 `agent_tasks` 任务，状态为 `QUEUED`。
4. Spring Boot 异步任务调用 Python Agent 的索引接口，Agent 解析资料并写入 ChromaDB。
5. Agent 根据用户选择或作业内容识别 Skill，比如实验报告、论文总结、课程问答或动态规划。
6. Agent 基于作业信息、Skill 信息和章节要求构造多路检索 query，在当前作业的 collection 中召回资料片段。
7. Agent 把检索证据、作业信息、Skill 指令和输出约束组合成 prompt，生成 Markdown 报告初稿。
8. 质量门控对初稿做结构、证据、具体性、成熟度和风险评估；如果证据不足或章节缺失，最多触发 1 轮补充检索并重生成候选稿。
9. 后端保存最终报告、质量指标、Agent trace 和任务日志，前端通过 SSE 展示进度，并通过定时刷新兜底补齐收尾阶段。

这个流程的重点是所有资料检索都限定在当前作业维度，避免不同作业之间资料串用。

### Q5：你提到作业级隔离，具体怎么保证不同作业的资料不会混在一起？

A：我在 RAG 设计里把 assignment 作为最核心的隔离边界。每个作业在 ChromaDB 里对应一个独立 collection，命名规则是 `assignment_{assignment_id}`。比如作业 1 的资料只进入 `assignment_1`，作业 2 的资料只进入 `assignment_2`。

生成报告时，Agent 只会检索当前作业对应的 collection，不会跨 assignment 搜索。重建索引时也只重建当前作业的 collection，并且使用 cosine space：

```python
metadata={"hnsw:space": "cosine"}
```

这样可以从数据结构上保证资料隔离，而不是只靠 prompt 约束模型“不要使用别的资料”。这点在作业系统里非常重要，因为不同课程、不同作业的资料混用会直接导致报告跑偏甚至产生错误引用。

## 三、资料解析与 RAG

### Q6：你是怎么处理用户上传的资料的？

A：上传资料后，Java 后端会把文件保存到本地 `storage/uploads/{assignmentId}`，并在 `materials` 表记录文件名、大小、路径和索引状态。用户触发生成后，Python Agent 根据文件类型解析内容：

- PDF 使用 `pypdf` 提取文本。
- Markdown 和 TXT 直接读取文本。
- 解析后的文本会按结构化策略切分，比如 Markdown 标题、PDF 页、普通段落和滑动窗口。

切分后，每个 chunk 会带上文件名、页码或段落位置、父子关系、摘要、关键词等 metadata，再调用 embedding 模型生成向量，最后 upsert 到当前作业的 ChromaDB collection。

### Q7：为什么不能直接把整份 PDF 塞给大模型？

A：直接塞整份 PDF 有几个问题。第一是上下文长度不可控，资料一多就会超过模型窗口或导致成本很高。第二是无关内容会干扰生成，模型可能抓不到真正和作业要求相关的部分。第三是可解释性差，后续很难说明某段结论来自哪份资料。

所以我采用 RAG。先把资料切成带 metadata 的 chunk，再根据作业要求召回最相关的片段。这样可以降低上下文噪声，控制 token 成本，也能在报告中保留 `[来源: filename]` 或更细粒度的 `[chunk_id: id]` 标注，方便后续做证据定位和评测。

### Q8：你的检索策略有什么特别设计？

A：我没有只用单一路径的 query，也没有完全依赖 LLM 自由改写 query，而是做了确定性的多路 query 扩展。当前主要有几类 query：

- assignment query：作业标题、课程名和作业描述。
- skill query：Skill 标签、必要章节和 `skill.query_hint`。
- section query：报告必要章节和作业要求。
- plan 或 keyword query：动态规划或关键词补充。

每路 query 分别做 embedding，再到 ChromaDB 检索候选 chunk，最后按 `chunk_id` 去重，并结合向量相似度、关键词、章节、文件名等信号做轻量 hybrid score。

这个设计的好处是稳定、可解释、成本低。相比自由式 query rewrite，确定性 query 更容易复现问题，也方便在 Agent trace 中记录每路 query 的命中数、去重后片段数和最终召回结果。

### Q9：如果检索召回不准，生成质量会受影响，你怎么评估和改进？

A：我在项目里准备了离线评测脚本 `agent-python/evals/eval_harness.py`，用 JSONL 数据评估检索和生成结果。支持的指标包括：

- `hit_rate_at_5`：前 5 个召回片段是否命中标准证据。
- `unsupported_claim_rate`：生成断言中没有证据支撑的比例。
- `skill_routing_accuracy`：任务类型识别准确率。
- `section_completeness`：必要章节完整率。
- `groundedness`：生成内容的证据贴合程度。
- `rewrite_trigger_rate`：自动改写触发率。
- `rerank_comparison`：对比 baseline 和 rerank 策略。

已有 hard case 中，加入 rerank 后 Hit Rate@5 从 50% 提升到 85%，Unsupported Claim Rate 从 29.8% 降到 15.3%。这说明检索链路不是只凭主观感觉调 prompt，而是可以用指标驱动优化。

## 四、任务类型识别与 Skill 体系

### Q10：为什么需要任务类型识别？所有作业共用一个 prompt 不行吗？

A：不太行。不同作业类型对结构和写法的要求差异很大。比如实验报告需要实验目的、环境、步骤、结果分析；论文总结需要研究背景、方法、创新点和不足；课程问答更强调概念解释和条理化回答。如果所有任务都套一个通用 prompt，生成结果会很泛，结构也不稳定。

所以我设计了 Skill 体系。业务 Skill 放在 `agent-python/app/skills/{skill_id}/` 下，每个 Skill 有：

- `skill.json`：机器可读元数据，包括 `system_prompt`、`query_hint` 和 `required_sections`。
- `SKILL.md`：更详细的生成说明，会加载到 `skill.instructions`。

这样每类作业都有自己的结构要求、检索提示和生成约束。

### Q11：系统怎么判断应该使用哪个 Skill？

A：路由分三层：

1. 如果用户手动选择了 Skill，就尊重用户选择。
2. 如果用户选择 `AUTO`，先走规则路由，根据标题、课程和描述里的关键词计算命中情况。高置信命中时直接选择 Skill。
3. 如果规则不确定，再调用 LLM 做路由。
4. 如果 LLM 也不能稳定判断，就兜底到 `dynamic_planner`。

这里的考虑是成本和稳定性。简单场景用规则就够了，不需要每次都调用 LLM；模糊场景再让 LLM 判断；开放型任务则交给动态规划生成报告结构。

### Q12：动态 Planner 的价值是什么？

A：固定 Skill 能覆盖常见任务，但真实作业经常比较开放，比如“结合课程资料分析某个系统设计方案”或者“围绕某主题完成综合报告”。这类任务很难提前写死章节。

动态 Planner 会先根据作业描述和检索材料规划报告大纲，再进入检索、生成、质量检查和必要改写流程。它的价值是让系统在没有命中固定 Skill 时仍然能产出结构合理的报告，而不是退化成一个通用聊天 prompt。

## 五、Prompt 与报告生成

### Q13：报告生成时 prompt 是怎么组织的？

A：生成 prompt 主要由五部分组成：

- 作业信息：标题、课程、描述和用户选择。
- 检索证据：RAG 召回的资料片段，带来源标签。
- Skill 元数据：必要章节、query hint 和任务类型说明。
- Skill 指令：`SKILL.md` 中的详细写作要求。
- 输出约束：只输出 Markdown 正文，不写元说明，不输出 TODO 或待补充，不编造来源。

我把 prompt 拆成这些模块，是为了让模型既知道“要写什么”，也知道“应该依据哪些资料写”，还知道“最终输出格式是什么”。这样比把所有要求混成一段自然语言更容易维护，也方便后续替换 Skill 或调整输出规范。

### Q14：你怎么减少模型幻觉和空泛表达？

A：我主要做了四层约束：

第一层是 RAG，生成时只提供当前作业召回的资料片段，并要求使用来源标注。

第二层是 Skill 结构，每类任务都有必要章节，避免模型自由发挥导致结构缺失。

第三层是输出约束，明确禁止 `TODO`、`TBD`、`待补充`、`资料不足` 等占位符，也禁止输出“以下是”“改写版”这类元说明。

第四层是质量门控，生成后会检查结构完整度、证据贴合度、具体性和风险。如果报告太空、章节不完整、证据不足或出现占位符，就会进入改写或要求用户补充资料。

## 六、质量门控

### Q15：质量门控具体检查什么？

A：质量门控分成模型审稿和本地规则两部分。

模型审稿主要看五个维度：

- `structure`：结构是否完整，层次是否清楚。
- `grounding`：是否忠实使用检索证据。
- `specificity`：是否有具体步骤、指标、方法和建议。
- `readiness`：是否达到可继续编辑的初稿成熟度。
- `risk`：是否存在幻觉、无依据断言、任务跑偏或资料不足。

本地规则主要检查必要章节是否完整、是否有明显占位符、报告是否过短、检索证据是否为空等。最终总分不是直接相信模型返回的 `total_score`，而是按本地权重重新计算：结构 25%、证据贴合 25%、具体性 20%、可编辑成熟度 15%、低风险 15%。

### Q16：为什么不直接让生成模型自己判断好不好？

A：生成模型自评容易偏乐观，而且同一个模型既生成又评价，会有明显的自我确认问题。我的设计是支持独立 evaluator 链路：如果配置了 `EVALUATOR_BASE_URL`、`EVALUATOR_MODEL` 和 `EVALUATOR_API_KEY`，质量检查会使用独立审稿模型；如果没配置，再回退到默认生成模型，保证本地演示不被额外配置卡住。

同时，本地规则会覆盖一些确定性问题，比如章节缺失、明显占位符、没有证据但内容很短等。这些问题不应该完全交给模型判断。模型审稿负责语义质量，本地规则负责硬约束，两者结合更稳。

### Q17：质量门控的决策结果有哪些？

A：主要有三类：

- `PASS`：达到合格可编辑初稿标准。
- `NEEDS_REWRITE`：结构、证据或具体性不足，但可以自动修复。
- `NEEDS_USER_INPUT`：资料不足、任务信息不足或需要用户确认，不能靠模型硬编。

当前通过阈值是 `QUALITY_PASS_SCORE=0.85`。这个分数表示“可以继续编辑的合格初稿”，不是最终可直接提交。这样定义比较符合产品场景，因为系统目标是辅助用户完成作业报告，而不是替用户保证最终提交质量。

## 七、自动改写与再次优化

### Q18：自动改写什么时候触发？会不会越改越差？

A：自动改写不是无条件触发，必须满足几个条件：报告非空，质量决策是 `NEEDS_REWRITE`，不是 `NEEDS_USER_INPUT`，没有明显人工确认类占位符，并且 Agent trace 没有超过最大步骤数。

如果低分原因更偏向“证据不足、grounding 偏低、章节缺失”，系统不会只在原有上下文里硬改，而是先进入一次轻量 Agentic RAG 修复：根据缺失章节、质量问题和 rewrite focus 生成补充 query，做第二次检索，合并新增证据后重生成候选稿并重新评估。这个补充检索严格限制为最多 1 轮，避免开放式循环。

改写策略也不是完全重写，而是“最小必要修补”。它重点修复结构、表达、具体性和来源标注，同时保留原稿中有效的内容、数据、结论和来源。

为了避免越改越差，我做了版本保护：

1. 保存初稿和初稿质量分。
2. 如果质量问题指向证据不足，先补充检索并尝试重生成。
3. 如果仍需要修结构或表达，生成改写稿。
4. 对改写稿重新评分。
5. 如果改写稿分数高于初稿，就采用新稿。
6. 如果改写稿分数未高于初稿，就保留初稿，并记录 `accepted_rewrite=false`。

这个机制可以防止 LLM 过度润色、删掉证据或引入无依据内容后覆盖原稿。

### Q19：用户手动编辑过报告后，再次优化怎么保证不覆盖用户修改？

A：再次优化不是简单重新生成。前端点击“再次优化”时，会先保存当前编辑器里的草稿。后端创建新的优化任务时，会把当前草稿、上一版质量分、作业信息和最新资料状态一起传给 Agent。

Agent 重新检索当前 assignment collection，但会在保留用户有效编辑的前提下优化结构、表达和证据引用。再次优化时，如果已经有上一版质量分，系统会直接使用上一版已保存质量分作为 baseline，不再重复给原稿打分；只评估候选稿，并且只有候选稿高于 baseline 才采纳。这样可以避免 LLM evaluator 对同一原稿重复评分时出现波动，比如上一版 91 分、本轮重评却变成 66 分，从而错误采纳低质量候选稿。

这样可以避免用户已经改好的内容被一次低质量生成覆盖。即使用户点击“重试”，后端也会保留失败任务的原始类型：原来是再次优化，就继续重试再次优化；原来是生成报告，才重试生成报告。

## 八、任务日志、异步执行与可观测性

### Q20：生成报告可能耗时比较久，你怎么处理前端等待和任务状态展示？

A：后端创建任务后不会阻塞 HTTP 请求，而是立即返回 `AgentTask`。真正的生成流程由 `AgentTaskRunner` 这个独立 Spring Bean 通过 `@Async` 执行，再调用 `AgentWorkflowService.runReportTask`。

这里特意把异步 runner 拆成独立 Bean，是为了避免同一个 Service 内部自调用绕过 Spring AOP，导致 `@Async` 不生效。

前端通过 `EventSource` 订阅 `/api/tasks/{taskId}/events`，后端每个阶段调用 `TaskLogService.push`，一边写入 `agent_task_logs` 表，一边通过 SSE 推给前端。Python Agent 还提供 `/agent/generate-report-stream` 和 `/agent/improve-report-stream`，以 NDJSON 形式把 `retrieve`、`generate`、`quality`、`rewrite`、`compare` 等阶段完成事件实时传给 Java 后端；Java 再转换为现有 SSE 日志。流式接口不可用时，后端会回退到非流式接口。

当前是“逐阶段/逐工具完成事件”，不是逐 token 流式输出。对于自动改写这种耗时阶段，前端会根据上一阶段结果推断出“自动改写进行中”的转圈状态，并且运行中任务每 5 秒定时刷新一次详情，避免最后的 `done`、`quality_final` 或 trace 因 SSE 断连没有及时显示。

### Q21：Agent 内部过程怎么做到可观测？

A：我把 Agent 的关键运行信息都沉淀到任务结果里，包括：

- 任务类型识别结果。
- 多路 query 数量和命中情况。
- 检索到的 evidence chunks。
- 报告质量评分和问题列表。
- 是否触发补充检索、自动改写、是否采纳候选稿。
- 每个阶段的 trace 和耗时。

这些信息会以 JSON 形式存到 `agent_tasks` 相关字段中，并且保持向后兼容，避免后续字段调整导致历史任务无法展示。前端除了展示任务进度，也有监控面板统计整体运行情况。

### Q22：监控面板看哪些指标？这些指标有什么用？

A：监控接口是 `/api/monitoring/overview`，数据来源包括 `assignments`、`materials`、`reports`、`agent_tasks`、`agent_trace_json` 和 `quality_metrics_json`。

当前主要指标包括：

- `totalTasks`：生成任务数。
- `taskCompletionRate`：任务完成率。
- `qualityPassRate`：质量门控通过率。
- `avgDurationSeconds` 和 `p95DurationSeconds`：平均耗时和 P95 耗时。
- `dynamicPlannerRate`：动态 Planner 使用比例。
- `rewriteTriggerRate`：自动改写触发率。
- `rewriteAcceptRate`：改写稿采纳率。
- `avgRetrievedChunks`：平均检索片段数。
- Skill 分布、阶段平均耗时、最近任务列表和资源统计。

这些指标可以帮助判断系统瓶颈。比如检索片段数偏低可能说明召回不足，改写触发率过高可能说明初稿 prompt 或 Skill 结构需要优化，P95 耗时偏高则说明某些阶段需要做缓存、并发或超时控制。

## 九、工程难点与解决方案

### Q23：你觉得这个项目最大的技术难点是什么？

A：最大的难点不是把 LLM 接起来，而是让生成链路稳定、可控、可解释。具体有五个方面：

第一，如何确保生成内容只基于当前作业资料。我用 assignment 级 collection 做硬隔离，并在 prompt 和来源标注上做软约束。

第二，如何适配不同作业类型。我设计了 Skill 路由和动态 Planner，避免所有任务共用一个通用 prompt。

第三，如何判断报告质量。我引入模型审稿加本地规则的质量门控，而不是只看文本长度或模型自评。

第四，如何避免自动改写或再次优化越改越差。我做了改写后重评和版本保护；再次优化直接使用上一版保存质量分作为 baseline，只采纳质量高于当前版本的新稿。

第五，如何把 Agent 黑盒过程变成可观测数据。我持久化了任务日志、Agent trace、检索证据、质量指标和阶段耗时，并在前端做了实时进度和监控面板。

### Q24：如果面试官问“你的项目亮点是什么”，你会怎么回答？

A：我会按优先级讲五个亮点：

第一是完整 Agent 闭环。项目覆盖资料解析、RAG 检索、任务路由、报告生成、质量检查、自动改写和再次优化，不是一次性文本生成。

第二是作业级 RAG 隔离。每个 assignment 都有独立 ChromaDB collection，避免不同作业资料混用。

第三是质量门控和版本保护。系统会独立检查结构、证据、具体性和风险，必要时触发补充检索或自动改写；再次优化使用上一版质量分作为 baseline，只保留更优版本。

第四是 Skill 路由和动态 Planner。常见任务用固定 Skill 保证结构，开放任务用动态规划生成大纲，兼顾稳定性和泛化能力。

第五是可观测和评测。后端持久化 Agent trace、检索证据和质量指标，前端展示 SSE 进度和监控统计，离线评测脚本支持 Hit Rate@5、Unsupported Claim Rate 等指标。

### Q25：这个项目相比直接调用 ChatGPT 有什么优势？

A：直接调用 ChatGPT 的问题是输入资料、任务结构、质量判断和过程追踪都不稳定。这个项目的优势主要有四点：

第一，资料可控。系统先解析并索引用户上传资料，生成时只检索当前作业资料，减少跑偏。

第二，结构可控。不同任务走不同 Skill，报告章节和写作要求更稳定。

第三，质量可控。生成后有质量门控，不合格时进入补充检索、自动改写或提示用户补充信息；已有报告再次生成或再次优化时不会轻易覆盖更高质量版本。

第四，过程可观测。每次任务的检索证据、质量指标、改写决策和阶段日志都会保存，方便调试和优化。

所以它更像一个面向作业报告场景的工程化 Agent 系统，而不是一个简单的聊天入口。

## 十、数据库与后端设计

### Q26：主要的数据表是怎么设计的？

A：核心表有五类：

- `assignments`：作业元信息，包括标题、课程、描述、截止时间、用户选择的 Skill、最终解析出的 Skill 和状态。
- `materials`：上传资料元信息，包括文件名、大小、存储路径和索引状态。
- `agent_tasks`：一次 Agent 任务，包括状态、当前阶段、任务类型识别结果、检索证据、质量指标和 Agent trace。
- `agent_task_logs`：任务阶段日志，用于前端 SSE 展示和历史追踪。
- `reports`：生成后的 Markdown 报告，支持版本递增、编辑和导出。

设计上我没有把 Agent 运行结果拆成大量强 schema 表，而是把 trace、quality metrics、evidence 等存成 JSON 文本。原因是 Agent 字段会随着实验快速变化，JSON 更利于兼容历史数据，也能避免频繁改 MySQL schema。

### Q27：为什么强调不要轻易改 MySQL schema？

A：因为这个项目里 Agent trace、检索证据和质量指标会持续迭代，如果每次新增一个指标都改表结构，迁移成本会很高，也容易破坏已有数据。当前策略是核心业务实体保持稳定 schema，Agent 的半结构化结果存在 JSON 字段中，并保证字段向后兼容。

这样既能满足前端展示和监控统计，又给 Agent 实验保留灵活性。

## 十一、异常、边界与安全

### Q28：资料不足或者用户描述太模糊时，系统怎么处理？

A：如果检索证据为空、报告过短、作业描述不足，或者模型判断需要用户补充信息，质量门控会返回 `NEEDS_USER_INPUT`。这种情况下系统不会强行自动改写，因为继续生成很可能会编造内容。

这也是我把 `NEEDS_REWRITE` 和 `NEEDS_USER_INPUT` 分开的原因。前者表示当前信息足够，但表达或结构需要修复；后者表示信息本身不足，需要用户补资料或补充要求。

### Q29：有没有考虑日志安全和敏感信息？

A：有。系统会记录阶段日志、Agent trace、检索摘要和质量指标，但不应该记录 API key、完整 prompt 或完整上传文档正文。日志重点服务于任务追踪和调试，而不是把所有输入输出原样落盘。

这点在接入外部 LLM 和用户资料上传时很重要。后续如果进一步产品化，还需要做用户隔离、文件权限、脱敏日志和更完整的审计机制。

## 十二、可以继续优化的方向

### Q30：如果继续做，你会优先优化哪些地方？

A：我会优先做五件事：

第一，继续增强质量评估的稳定性。当前 evaluator 分数可以作为工程质量门控信号，但同一篇稿件在不同轮次可能存在几分甚至更大的波动。后续会固定低温度评估、补充 few-shot 标尺、引入同稿评分缓存、多评估器投票或多次评分取均值，并把规则分和模型分做更稳的加权融合。

第二，删除单个资料时同步删除对应 chunk，进一步增强向量库和材料表的一致性。

第三，把 Agent 内部阶段进一步细化为“开始事件 + 完成事件”，让 SSE 不只是阶段完成后更新，而是能在自动改写、质量检查等长耗时阶段开始时就显示运行态。

第四，引入更系统的 claim-evidence 评估，把报告中的关键断言和检索证据做自动对齐，提升来源标注可信度。

第五，对扫描版 PDF 增加 OCR，或者在无法解析时明确提示用户资料不可读。

### Q31：评估器分数波动比较大，面试官追问时怎么回答？

A：我会把它作为后续优化方向来讲，而不是回避。

质量门控里的 evaluator 本质上还是 LLM-as-judge，它适合做工程上的自动审稿信号，但不是绝对客观分数。实际测试中，同一篇稿件如果在不同上下文、不同轮次、不同 prompt 细节下重新评分，可能出现明显波动。这个问题会影响版本保护，所以我在工程上做了两层处理：

第一，再次优化时不再重复给原稿打分，而是使用上一版已保存质量分作为 baseline，只评估候选稿，避免同一原稿被重新评成更低分后错误采纳新稿。

第二，生成或改写候选稿后仍然要和 baseline 比较，只在候选稿质量更高时采纳，低分稿不会覆盖用户当前版本。

后续我会从评估稳定性继续优化，比如固定 evaluator 的低温度配置，设计更明确的 rubric 和 few-shot 标尺，对同一版本报告做评分缓存，引入多次评分取均值或多评估器投票，并用 claim-evidence 对齐和规则分降低纯模型打分的随机性。

面试时可以总结成一句话：当前质量分是工程质量门控，不等价于教师评分；我已经用版本保护降低波动带来的覆盖风险，后续会通过评分缓存、多评估器和断言级证据校验进一步提升稳定性。

### Q32：如果面试官追问“你这个项目还有什么不足”，怎么回答比较好？

A：我会坦诚讲三个不足，同时说明改进方向。

第一，当前 Agent 已支持逐阶段事件流，但还不是逐 token，也不是所有阶段都有 start event。比如自动改写耗时较长时，前端现在主要靠推断运行态和定时刷新兜底。后续可以补齐阶段开始事件，进一步提升实时性。

第二，当前质量门控已经能识别结构、证据和占位符问题，但 claim-evidence 粒度还可以更细。后续可以把报告拆成断言级别，逐条验证是否有证据支撑。

第三，资料解析对普通 PDF、Markdown 和 TXT 比较友好，但扫描版 PDF 还需要 OCR 支持。后续可以引入 OCR 或在解析失败时给用户更明确的交互提示。

这样的回答既不回避问题，也能体现我知道系统下一步该怎么演进。

## 十四、简历逐条追问

### Q34：简历里写“将大模型生成过程从不可控制改造为可观测、可追踪、可预测、可优化”，面试官问你具体怎么做到的？

A：我会从四层回答。

第一是可观测。每次生成都会落库 `agent_tasks`、`agent_task_logs`、`agent_trace`、retrieved evidence 和 quality metrics，前端能看到资料解析、检索、生成、质量检查、补充检索、改写、完成这些阶段，而不是只看到一个最终文本。

第二是可追踪。报告里会保留检索证据，trace 里记录每一步输入输出摘要、耗时、检索片段数和质量评分，所以当报告质量不好时，可以定位是资料解析问题、检索召回问题、生成问题还是质量门控问题。

第三是可预测。系统没有让模型自由决定无限循环，而是限定为固定上限的 Agent Loop：检索、生成、质量检查、最多一轮补充检索、最多一次改写。这样成本、耗时和行为边界都比较可控。

第四是可优化。我沉淀了 Hit Rate@5、Unsupported Claim Rate、质量通过率、改写触发率、P95 耗时等指标，可以基于数据去判断 rerank、query 扩展、质量门控和改写策略是否真的有效。

### Q35：简历里写 Agent Workflow，但你没有用 LangChain 或 LangGraph，面试官追问怎么办？

A：我会说这个项目的 Agent Loop 是自研的轻量工作流，不是因为不知道 LangChain / LangGraph，而是因为当前需求更适合可控、可解释、易落库的固定流程。

这个系统的核心不是开放域多 Agent 协作，而是作业报告生成里的确定性链路：资料解析、RAG 检索、生成、质量评估、必要时补充检索和改写。每一步都要和 Java 后端任务状态、SSE 日志、MySQL 持久化、前端 trace 展示强绑定。如果直接套 LangGraph，确实能表达图结构，但会引入额外抽象和调试成本；而我当前的流程节点数量少、边界清楚，用自研 loop 更方便控制最多几轮、如何保存 trace、如何做版本保护。

面试里可以补一句：如果后续要做更复杂的多角色协作，比如 Planner、Retriever、Writer、Reviewer、Citation Verifier 分离，并且存在多轮条件跳转，我会考虑引入 LangGraph；但当前阶段我优先选择轻量实现，保证稳定性和可观测性。

### Q36：简历里写 Qwen3-Rerank、Hit Rate@5 和 Unsupported Claim Rate，面试官可能会问这些指标怎么算？

A：Hit Rate@5 衡量的是检索质量。对于每条 hard eval case，我会预先标注或判断哪些资料片段是回答这个任务必须召回的证据。如果 Top-5 检索结果里命中了关键证据，就算 hit。加入 Qwen3-Rerank 后，Hit Rate@5 从 50% 提升到 85%，说明 rerank 能把更相关的片段排到前面。

Unsupported Claim Rate 衡量的是生成可靠性。我会抽取或人工检查报告中的关键结论，看它们是否能被检索证据支撑。如果报告提出了材料里没有依据的结论，就计入 unsupported claim。这个指标从 29.8% 降到 15.3%，说明更好的检索排序能减少模型基于不充分上下文进行发挥。

这里我不会把它夸大成“事实准确率”，而是说它是离线评测里的工程指标，用来比较不同检索策略对生成可靠性的影响。

### Q37：简历里写“动态规划触发率”，这里会不会被理解成算法动态规划？

A：这个词确实容易有歧义。项目里的“动态规划”指的是 dynamic planner，也就是当固定 Skill 没有高置信命中时，由 Agent 先规划报告大纲和章节结构，不是算法里的 Dynamic Programming。

如果是简历，我建议把“动态规划触发率”改成“动态 Planner 触发率”或“动态报告规划触发率”。面试时如果被问到，我会解释它是任务路由兜底策略：实验报告、论文总结、课程问答这些固定 Skill 都不匹配时，系统会动态生成报告结构，再围绕这个结构检索资料和生成正文。

### Q38：简历里技术栈写 Skill、RAG、Agent Workflow，会不会显得概念多但框架少？

A：我觉得不需要为了显得高级硬加 LangGraph、Graph RAG、Mem0。对实习简历来说，关键不是堆框架，而是能讲清楚你解决了什么工程问题。你现在的项目已经有作业级资料隔离、多路检索、rerank、质量门控、自动改写、再次优化版本保护、任务日志和监控，这些比“用了某个框架”更能体现你真的做过系统。

但简历可以稍微优化表达：技术栈里保留 Spring Boot、FastAPI、ChromaDB、MySQL、SSE、Docker、DeepSeek、Qwen3-Rerank；`Skill`、`RAG`、`Agent Workflow` 更适合放在核心功能或项目亮点里，不一定都塞进技术栈。这样看起来更像工程项目，而不是关键词堆叠。

## 十五、推荐讲解顺序

### Q39：面试时这个项目应该怎么讲，顺序会比较自然？

A：我会按下面顺序讲：

1. 先讲项目背景：课程资料分散，纯 ChatGPT 容易跑偏，缺少来源、结构和质量检查。
2. 再讲整体架构：Next.js 前端、Spring Boot 后端、FastAPI Agent、ChromaDB、MySQL。
3. 然后讲核心链路：上传资料、解析切片、向量化、Skill 路由、RAG 检索、生成报告、质量门控、自动改写、保存和监控。
4. 接着重点讲难点：资料隔离、检索召回、任务类型适配、质量判断、改写版本保护和可观测性。
5. 最后讲量化和反思：Hit Rate@5、Unsupported Claim Rate、质量通过率、改写触发率、P95 耗时，以及后续优化方向。

这样的顺序比较符合面试官的理解路径：先知道你做了什么，再知道系统怎么跑，最后看你解决了什么难问题。
